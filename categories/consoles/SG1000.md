# Introduction
The SG-1000 combines a Z80 CPU with separate video and sound chips.
For a first disassembly, its small RAM area and mirrored I/O ports are useful landmarks: they help distinguish game state, graphics transfers and sound writes [^2] [^3] [^4].

Sega released its first home console in Japan on 15 July 1983, alongside the SC-3000 computer and on the same day as Nintendo's Famicom.
[Sega's hardware history](https://www.sega.jp/history/hard/column/column_01.html) explains how the SG-1000 adapted the SC-3000 design into a games machine [^1].

# Hardware and Memory Map
MAME's [SG-1000 driver](https://github.com/mamedev/mame/blob/774a180df2b6ef9c53e48337792256817c50f768/src/mame/sega/sg1000.cpp) records a Z80A running at approximately 3.58 MHz, a TMS9918A video display processor (VDP), and an SN76489A sound generator for the boards it documents.
Its board notes and machine configuration are useful companions to chip manuals, but an emulator implementation is not a substitute for checking the particular hardware revision [^2].

The [SMS Power memory map](https://www.smspower.org/Development/MemoryMap) describes the ordinary SG-1000 address space as follows [^3]:

CPU addresses | Contents | Reversing implication
---|---|---
`$0000-$BFFF` | Cartridge ROM, RAM or other cartridge hardware | Check the cartridge before assuming the whole range is ROM
`$C000-$C3FF` | 1 KiB of system RAM | Start here when identifying game-state variables
`$C400-$FFFF` | Mirrors of that RAM, repeated every 1 KiB | Different addresses may refer to the same byte

For example, `$C123`, `$C523` and `$FD23` all select offset `$123` in ordinary system RAM.
When annotating a trace, normalise RAM addresses with `$C000 | (address & $03FF)` to avoid inventing several variables for one storage location.
Cartridges can disable system RAM and take over the address space, so apply this rule only after identifying the mapping [^3].

# Finding Video and Sound Routines
The Z80 accesses these devices through I/O instructions, separately from its memory reads and writes.
The [SG-1000 I/O port map](https://www.smspower.org/Development/IOPortMapSG) gives these useful ranges [^4]:

I/O port | Write | Read
---|---|---
`$40-$7F` | SN76489 sound data | Open bus
Even ports in `$80-$BF` | VDP data | VDP data
Odd ports in `$80-$BF` | VDP control | VDP status

A search for writes to `$BE` alone can miss graphics code using `$80`: both select the VDP data port.
Follow the surrounding address-setup and transfer instructions before labelling a routine as a tile loader.
Likewise, read and write accesses to `$BF` have different meanings [^4].

Controller decoding needs more care.
SMS Power lists controller reads across `$C0-$FF`, while the pinned MAME driver routes `$DC-$DF` through its peripheral handlers.
If a trace uses another alias, check the documentation and emulator implementation separately rather than treating their maps as identical [^2] [^4].

## Try an I/O Watchpoint
With an SG-1000 cartridge running in MAME's debugger and the Z80 selected, enter `wpiset 80,40,w` to stop on writes in the video-port range.
MAME's [watchpoint documentation](https://docs.mamedev.org/debugger/watchpoint.html) explains that `wpiset` selects I/O space and that the second argument is a length [^5].

Resume execution and inspect the instruction stream at a stop.
Compare the port, the value written and the preceding setup code; repeat during a screen transition to find a larger transfer.
Use `wplist` to see the watchpoint number, then `wpclear` followed by that number to remove it [^5].
This is a starting point for tracing a game's graphics path, not a claim that every write transfers visible tile data.

The [SMS Power document collection](https://www.smspower.org/Development/Documents) links the Texas Instruments TMS9918A data sheet for interpreting video-register writes.
Keep the SG-1000's chip documentation beside any [Master System](/mastersystem) reference rather than assuming the later machine's video features apply.
